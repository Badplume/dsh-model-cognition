# 多模型会审

`model_panel` 把**同一个问题**并行发给多个模型，各自返回答复。
它的价值不在"多几个答案"，而在**答案不一致的地方**——那里通常藏着真正的风险。

```
model_panel({
  models: ["deepseek/deepseek-chat", "openai/gpt-4o-mini", "anthropic/claude-sonnet-4"],
  prompt: "……",
  system: "……",              // 可选，对所有模型生效
  purpose: "评审限流方案"
})
```

返回 `results` 数组（每个模型一项，`status` 为 `ok` 或 `error`）、
`totalCostUsd`、以及 `skipped`（引用写错、在发出前就被跳过的模型）。
**一个模型失败不影响其他模型**——某个供应商超时或密钥失效时，其余结果照常可用。

## 什么时候值得

- **要给重要判断挑错**：架构选型、数据模型、并发方案、有安全含义的改动。
- **有争议的事实**：几个来源说法不一致，想让不同模型分别表态。
- **用户明确要求**比较几个模型。
- **你要交付一个有风险的东西**，想先看看别人会不会发现你漏掉的问题。

不值得：日常小问题、能查证的事实、你自己已经很确定的答案。
多个模型意见一致并不构成证明——它们可能一起错。

## 问题要怎么写

会审的效果几乎全部取决于 prompt。三条规则：

1. **先给上下文，再给问题**。参与的模型看不到本对话，也看不到彼此的答案。
2. **要求它给出可检验的东西**：具体是哪一行、哪个假设、什么条件下会失效。
   只要它说"这样做可能有风险"的回答，是没有用的。
3. **别暗示你倾向哪个答案**。写成"评审这个方案，指出它会在什么情况下出错"，
   而不是"你觉得这个方案是不是有问题"。

好的会审 prompt 长这样：

```
下面是我们打算采用的限流方案，请评审并指出它在什么情况下会失效：

<方案>
……
</方案>

如果发现缺陷，请给出：(1) 触发条件；(2) 后果；(3) 最小修改建议。
如果没有发现缺陷，请明确说"未发现缺陷"，不要为了显得有用而编造问题。
```

最后一句很重要：**不给"必须找出问题"的压力**，否则模型会为了交差而虚构缺陷。

## 结果怎么读

按你的判断成本从低到高：

1. **一致且具体** —— 可信度提高，但仍然要自己核实关键事实。
2. **一致但空泛** —— 说明 prompt 没问到位，或者这个问题不值得会审。
3. **不一致** —— 这是最有价值的情况。**不要投票**。去看它们分歧的**理由**：
   - 分歧来自**前提不同**（对某个约束的理解不一样）→ 说明需求本身有歧义，去问用户或查事实。
   - 分歧来自**事实错误**（某个模型编了 API）→ 你可以直接查证，不需要再问。
   - 分歧来自**真正的取舍**（性能 vs 简单、一致性 vs 可用性）→ 这是要交给用户的决定。
4. **某个模型失败** —— 在报告里说明哪个没答上来、错误是什么，不要把它的缺席当成默认同意。

向用户报告时：

- 说清**每个结论出自哪个模型**，不要合并成"模型们认为"。
- 优先呈现**分歧**和你对分歧的判断，而不是四个答案的流水账。
- 你仍然是做结论的人。会审给你证据，不替你做决定。

## 成本

会审是**并行的**，并发数由设置里的 `concurrency` 决定，所以并没有想象中慢；
但花费是各模型之和，通常比单次调用贵好几倍。

- 会审的每一次调用**各自**过预算闸门。某个模型太贵时会单独返回 `pending_approval`，
  其他便宜的模型照常执行——这种"部分需要批准"是正常的，照实报告给用户。
- 模型越多不代表越好。**2–3 个来自不同供应商的强模型**，通常好过 6 个同源的。
- 用 `purpose` 写清这次会审的用途，事后在 `model_usage` 里能看清钱花在哪。
