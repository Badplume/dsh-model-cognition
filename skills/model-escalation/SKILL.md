# 把难题交给更强的模型

有些问题，问一次外部模型比你自己反复试更划算。这个 skill 讲的是**怎么交得干净**——
绝大多数"问了也没用"的情况，原因不是模型不行，而是移交说明里缺了它需要的东西。

## 先判断值不值得

值得外包：

- **你已经试过并失败**，而且失败原因不是"信息不足"。
- **需要长链条推理**：多步约束、需要同时满足若干条件的设计问题。
- **需要特定的领域知识**：某个语言/框架的细节、某个数学方法、某类法规或协议。
- **要一块独立产出**：写一个完整函数、写一段测试、翻译一整段文档、把一段逻辑从一种语言改写成另一种。
- **用户的当前模型明显不擅长**这类任务，而他还配置了别的模型。

不值得：

- **缺信息**。模型不知道你仓库长什么样——先把文件读出来，再问。
- **你自己能做**，只是想省事。移交 + 阅读 + 核实，往往比自己写更慢。
- **需要动手验证**的东西（跑测试、看渲染结果）。模型只能给建议，验证还得你来。

## 移交说明的六个部分

一份好的移交说明，让一个**看不到你对话、看不到你仓库**的人能独立完成这件事。
六个部分：

1. **目标**：要产出什么，一句话说清。
2. **上下文**：它需要的全部背景。代码、数据结构、约束、错误信息，都贴进去。
3. **约束**：语言/版本、不能用什么、必须遵守什么规范、性能或体积要求。
4. **已试过的做法与结果**：这能挡掉它给出你已经失败过的方案。
5. **产出形式**：整段代码？补丁？分点解释？只要结论？**明确说**。
6. **验收标准**：你怎么判断这个答复能不能用。

## 一个可用的模板

```
你是一个资深 <领域> 工程师。请在不追问的前提下完成下面的任务。

## 目标
<一句话>

## 背景
<代码 / 数据结构 / 报错 / 相关事实，全部原文贴出>

## 约束
- 语言与版本：<…>
- 不能引入新依赖 / 必须保持 <某接口> 不变 / 必须兼容 <某版本>
- <其他硬性要求>

## 我已经试过
- <做法一> → 结果：<失败原因>
- <做法二> → 结果：<失败原因>

## 你需要输出
1. <产出物一>（完整可粘贴，不要省略号）
2. <产出物二>
3. 如果你认为题目本身有问题，直接说明，不要勉强作答。

## 我会怎么验收
<验收标准>
```

两个细节值得单独说：

- **"不要省略号"**。否则你会收到一段 `// ... 其余逻辑不变` 的代码，等于没给。
- **允许它说"这题有问题"**。禁止质疑的提示词会换来一个看起来完整、实际错误的答案。

## 拿到答复之后

**你必须验证**。外包出去的结论仍然是你的责任：

- 代码：真的粘进去跑一遍、跑测试。模型经常会用不存在的 API、
  传错参数顺序、忘掉显而易见的边界。
- 事实：至少找一个独立来源核对。
- 设计建议：按它给的条件构造一个例子，看看是不是真的成立。

然后**用自己的话**把结果讲给用户，并说明哪部分来自外部模型。
如果它给的方案不成立，不要为了不浪费这次调用就硬用——说清为什么不成立，
必要时带着新的信息再问一次（**新信息很关键**，重复同一个问题通常得到同一个错误答案）。

## 与子代理的区别

如果你要的不只是"一段答复"，而是**一个有工具的 agent 去动手做事**，
那用 Harness 自己的子代理机制（可以指定不同的 provider 和 model），
而不是 `model_ask`。`model_ask` 发出去的是一次纯文本问答：
对方没有文件系统、没有工具、看不到你的会话。

## 成本提示

外包给强模型的单次调用通常不便宜，容易触发预算闸门。
把问题和上下文一次写全，比分成四五次试探着问更省钱。
被 `pending_approval` 拦住时，把完整的移交说明和预估花费一起呈现给用户，
让他一次决定，而不是拆成小请求反复申请。
