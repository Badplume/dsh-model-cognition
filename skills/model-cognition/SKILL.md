# 调用其他模型

这个 Harness 里装了一个叫 **Model Cognition** 的插件，它把用户配置好的其他大模型接入对话，
让当前 agent 可以把一个问题发给另一个模型，并把答复当作资料使用。

你是**主动方**：什么时候值得问别人、怎么问、结果怎么用，都由你判断。

## 先看清有什么

```
model_list()
```

返回可用的 `providerId/modelId` 列表、每个供应商的密钥是否就绪、以及当前的预算设置。
**在第一次调用之前先跑它一次**：没有配置模型时你应该直接告诉用户去配置，
而不是反复尝试调用。

模型引用格式是 `providerId/modelId`，例如 `deepseek/deepseek-chat`、`openai/gpt-4o-mini`、
`ollama/qwen2.5:14b`。也可以只写模型 id（例如 `deepseek-chat`），
但只有在**恰好一个**供应商提供它时才会自动匹配成功。

## 什么时候真的该问

值得：

- **你确实不确定**，而且另一个模型可能知道——某个库的具体 API、某个版本的行为差异、某个概念的准确定义。
- **需要第二种意见**：你要下一个重要判断，想看看别的模型会不会得出同样结论。
- **用户明确要求**用它配置的其他模型来做事。
- **任务明显更适合另一个模型**：用户配置了一个专门的代码模型或推理模型，而这正是当前任务。
- **平行比较**：同一个问题想让几个模型分别答（用 `model_panel`）。

不值得：

- **你自己就能答**。多问一次要多花时间和钱，而且答案更差时你还得判断该信谁。
- **答案是事实性的、可以查证的**。查文档、读代码、跑一遍，比问一个模型可靠得多。
- **需要当前会话的上下文**。别的模型看不到你的对话，除非你把上下文写进 prompt。
- **用户没有配置任何模型**。先让他去配置。

一句话：**把外部模型当成一位不在场的同事**——值得专门去问一句的，才去问。

## 怎么问

```
model_ask({
  model: "deepseek/deepseek-chat",       // 省略则用设置里的默认模型
  prompt: "……",
  system: "……",                          // 可选，固定角色或输出格式
  maxTokens: 2048,                        // 可选，覆盖默认
  purpose: "核对 Rust 生命周期规则"        // 可选，写进用量账本，便于复盘花费
})
```

其他模型**看不到本次对话**。prompt 必须自包含：

- 把它需要的背景、代码、约束都贴进去，不要写"上面那个文件"。
- 明确说清你要什么形式的结果：一段解释、一段代码、一个 JSON、一个是/否加理由。
- 一次问一件事。三件事混在一个 prompt 里，回答质量会明显下降。
- 需要它保持某种身份或风格时，用 `system`，不要塞进 prompt。

## 答复怎么用

返回的 `text` 是**资料，不是结论**。

- 把它和你要说的话分开：向用户转述时说明这是哪个模型的意见，不要冒充自己的判断。
- **外部模型说的也要核实**。它可能编造 API、记错版本号、把两个库混在一起。
  涉及要写进代码、要执行、要交付的内容，你仍然要自己验证。
- 几个模型给了互相矛盾的答案时，不要挑一个顺眼的；把分歧本身报告给用户，
  或者去找能判定的事实（文档、代码、实验）。

## 花费与预算

每次调用都会记录进账本：

```
model_usage({ limit: 20 })          // 最近调用、今日花费、待批准项
```

设置里有三道闸：单次上限、每日上限、自动放行阈值（都以美元计）。
**只有用户填过价格的模型才会计价**；未定价的模型显示"未定价"，不会计入预算判断。

当预估花费超过自动放行阈值时，`model_ask` 不会真的发出，而是返回：

```
{ status: "pending_approval", approvalId: "ap-…", reason: "预估 $0.012，超过自动放行阈值 $0.005" }
```

这时：

1. **告诉用户**：要问哪个模型、问什么、大概多少钱，并给出 `approvalId`。
2. 等用户在 **设置 → Model Cognition → 用量与预算** 里批准或拒绝。
3. 批准后，用**完全相同的 `model` 与 `prompt`**，带上 `approvalId` 重试：

```
model_ask({ model: "…", prompt: "…", approvalId: "ap-…" })
```

批准是**一次性的**，而且绑定那一次的具体请求——换一个问题就要重新批准。
被拒绝、过期或改动过 prompt 时，重试会再次返回 `pending_approval`，这是正常的，不要反复重试。

不要为了绕过闸门而改写 prompt、拆分请求或换成别的模型。那些上限就是用户划的线。
如果确实需要更大的额度，说明理由，让用户自己在设置里改。

## 出错时

工具会直接抛出供应商的原始错误，常见的有：

| 现象 | 含义 | 你该做的 |
| --- | --- | --- |
| `401` / `403` | 密钥无效或没权限 | 告诉用户去 设置 → Model Cognition → 供应商 检查密钥 |
| `还没有配置 API Key` | 该供应商没填密钥 | 同上 |
| `请求超时` | 超过设置里的超时时间 | 可以调小 `maxTokens` 重试一次，或在设置里调大超时 |
| `无法连接 …` | 网络/地址不通 | 检查 baseUrl；本地模型要确认服务已启动 |
| `没有配置名为 … 的模型` | 引用写错了 | 跑一次 `model_list()` 看准确 id |
| `已被停用` | 用户停用了该供应商 | 换一个，或问用户 |

## 与其他 skill 配合

- 要让**多个模型互相比较或辩论** → `model-panel`
- 要把**一整块难题外包**给更强的模型 → `model-escalation`
- 要理解**预算闸门和审批流程** → `model-budget`
- 用户要**新增供应商/填密钥/填价格** → `model-setup`
